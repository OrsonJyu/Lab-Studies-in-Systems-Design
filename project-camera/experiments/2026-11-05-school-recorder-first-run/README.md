# 2026-11-05 · school 共用有线基线下首次运行录制程序

日期：2026-11-05（香港）12:14–14:56。用户在学校接好硬件，要求确认能否看到实时画面。这是共用有线基线（D014）在学校现场的第一次实际使用，也是录制程序（运动检测 + 滚动缓存）第一次在学校运行。没有改代码和配置。

## 过程与结果

1. **只读网络检查（12:14）**：有线链路、静态地址、两条路由、板卡 SSH、摄像头 RTSP 与 ONVIF 端口、板卡主机密钥共 9 项通过；"板卡远程状态"一项为警告，因为当时还没有登录会话。报告原件含地址，保存在被忽略的 `.local/` 中，这里只摘要。
2. **板卡失联一次**：用户启动"开始录制"后，SSH 短暂可用，随后板卡 ping 和 SSH 都不通；同一时间摄像头仍可达、Mac 网口仍有链路。用户重新插电后板卡恢复，按 uptime 推算重新启动于 12:23。
   - 上一次启动的用户日志只有开机后几十秒的桌面服务记录（时间戳仍是校时前的板卡时间），没有出错信息；系统日志需要 adm 组权限，本次没有读取。
   - **原因未确定**：电源/供电不足、系统卡死或网线松动都可能，本次没有能区分它们的证据。
3. **时钟**：重启后 ROCK 与 Mac 相差约 0.1 秒以内（单次读取估算），录制时间可信。**摄像头断电后没有保住手动设置的时间**：时间方式回到 NTP，比 ROCK 慢 29,313 秒（约 8 小时 8 分），画面左上角显示为 06:47 而实际是 14:56（见 [live-frame.jpg](live-frame.jpg)）。这回答了[摄像头校时记录](../2026-11-05-home-camera-clock-set/README.md)中"断电后能否保持"未测的问题：不能。录像事件时间用 ROCK 时钟，不受影响。
4. **录制程序**：重启后录制程序与网页都在运行，切片与检测两个 FFmpeg 进程正常，滚动缓存 60.1 秒。12:23–14:56 共保存 **86 个事件**（每小时 20–34 个），全部完整（无缺段、无 partial），均按静止 5 秒结束；实际保留的触发前时长 4.00–5.93 秒；片段时长中位数 12 秒、最长 36 秒，合计约 19 分钟，占用 209 MB。Mac 本地 `recordings/` 已有 97 个片段（含此前在家的片段）。
5. **实时画面**：从网页的实时流取 4 秒得到 42 帧 JPEG（约每秒 10 帧），画面内容为桌面与隔板（[live-frame.jpg](live-frame.jpg)）。

## 解读

- 学校现场的有线基线可用，录制程序能连续运行约 2.5 小时、事件完整。
- 86 个事件大多不是有意的测试动作：场景里没有守宫，触发来自环境变化（人走动、光线等，未逐个核对）。这说明当前全画面检测在真实环境下误触发很多，正是此前讨论的"定位守宫 / ROI / 排除整体变化"需要解决的问题。
- 摄像头没有电池保持时间，每次断电都要重新设置；可在"开始录制"里检测到偏差后自动校时（需用户同意改脚本）。
- 板卡失联需要再观察：如再出现，应换电源或插座，并用 `sudo journalctl -b -1` 读系统日志（看是否有欠压、过热或内核错误）。本次 CPU 温度读数 56.7 °C。

## 限制

- 失联原因未查明；系统日志未读。
- 86 个事件的触发原因没有逐一查看录像确认。
- 时钟偏差为单次 SSH 读取的粗略估算。
- 未测长时间（数小时以上）运行和断流恢复。
