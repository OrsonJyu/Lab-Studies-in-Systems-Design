# 2026-11-05 · home 码流与接口只读探测

日期：2026-11-05（香港），Mac UTC 2026-11-04 18:20–18:27。这是运动触发录制前的第 0 步：只读查询摄像头接口和码流参数，**不改摄像头设置、不订阅事件、不保存录像**。结构化结果见 [result.json](result.json)。

## 问题

1. 主码流和子码流的实际分辨率与关键帧间隔（决定预录能精确到多细）。
2. 摄像头是否提供运动事件，以及有没有可以回看历史画面的录像/回放服务。
3. ROCK 软件解码子码流和主码流各占多少 CPU（决定运动检测能不能放在板卡上）。

## 条件与方法

- 环境 `home`，共用有线基线（D014）；Mac 有线链路这次协商为 100BASE-TX 全双工。
- 共用只读检查器第一次运行时，本机地址和路由正常，但板卡 SSH、摄像头 RTSP/ONVIF 的 TCP 连接和主机密钥检查失败；ping 两台设备后立即重跑，除需要登录的远端状态外全部通过。没有确定首次失败的原因（可能与链路/ARP 刚建立有关），记为未解释的一次性现象。
- 板卡命令通过用户此前已认证、仍在运行的 SSH 会话执行；助手没有输入密码。
- [onvif_probe.py](onvif_probe.py)：只发送 ONVIF `Get*` 请求（时间、设备信息、服务、能力、配置文件、流地址、事件属性）。流地址只经板卡私有目录中 0600 权限的临时文件传给下一步，不打印。
- [stream_probe.py](stream_probe.py)：用 ffprobe 读取每路 12 秒的视频包（关键帧标记、时间戳）；用 FFmpeg 将子码流软件解码 30 秒、主码流 15 秒到空输出，统计 CPU。结束时删除临时流地址文件并核对。
- 两个脚本都从 Mac 经 SSH 标准输入在板卡运行，没有安装软件。

## 能支持的结论

- **预录粒度**：关键帧每 2 秒一个，按关键帧切段时，触发前保留时长只能按约 2 秒的倍数取；`p` 应不小于检测延迟加一个关键帧间隔。
- **运动检测位置**：板卡解码子码流负担很小，在 ROCK 上做帧差检测可行；主码流也能解码，但不必要。帧差检测需要另装 NumPy 或 OpenCV，或改用 FFmpeg 自带的滤镜。
- **摄像头自带运动事件**：接口存在，可作为第二个触发源和对照；但这次只读取了公告的主题，没有订阅、没有收到事件，触发灵敏度和延迟未知。
- **“直播回看”**：这台摄像头通过 ONVIF 没有历史录像回放能力；往回看的画面需要 ROCK 自己的滚动缓存提供。没有检查网页管理界面或摄像头存储卡功能。

## 限制

- 只读一次、每路 12 秒；没有测端到端延迟、首帧等待时间或长期稳定性。
- 解码 CPU 只包括 FFmpeg 解码到空输出，不含运动分析、分段写入或网页服务。
- 型号字符串和 GK7205V200 芯片名来自 ONVIF 自报信息，没有拆机或对照官方资料核实；不覆盖实物标签记录。
- 检查器首次 TCP 失败原因未确定。
